# End-to-end validation report: data-engineering-agent

Date: 2026-11-21. Repository: github.com/nikhiljii/data-engineering-agent- at commit `365d5d0`.
Method: a working copy was made, nothing was pushed to GitHub. Git tags in the working copy mark each stage:
`e2e-baseline` -> `e2e-arch-approved` -> `e2e-plan` -> `e2e-build-v1` (evaluator VETO) -> `e2e-build-v2` (evaluator PASS) -> final.

## 0. Read this first: how the "agents" were executed

The repo defines 17 agents in `.claude/agents/*.md`. In this environment they are **not registered as native subagent types**
(the Agent tool answered "Agent type 'architect' not found"). Each agent was therefore run as an **isolated general-purpose subagent
whose instructions were the repo's agent file, CLAUDE.md, the skill files and a brief**. Consequences, stated plainly:

- Real, separate runs with their own context happened (requirements-analyst, architect, orchestrator, quality-engineer, two pipeline-builder
  instances, evaluator twice, deployment, incident). Their outputs below are their real outputs.
- This is **not** a test of Claude Code's native `.claude/agents` mechanism, nor of its tool restrictions: every run had general-purpose tools
  and was only *told* its limits. Tool-limit enforcement is NOT TESTED.
- The orchestrator could not spawn nested agents. It wrote the plan and five briefs; this harness session acted as the dispatcher.
  Autonomous orchestrator-to-specialist delegation is therefore BLOCKED, not demonstrated.
- The same underlying model played all roles. The evaluator's independence is procedural (separate context, own queries, ground truth the
  builder never saw), not an independent model.

## 4. Architecture decisions

- Paradigm ELT (scorer: ELT 7 / ETL 0; the architect agreed). Two caveats the architect recorded: the scorer reason "SQL-strong" fires on `transforms.style: sql` although the profile has `sql_strength: medium`, and `pii: true` with `mask_before_landing: false` does not trigger the ETLT path. The decision rests on a profile whose team skill and SLA values were placeholders.
- ADR-002: plain SQL + Python on DuckDB, code under `scenario/ecommerce/` (not dbt; the conformance checker cannot see it). ADR-003: defect handling and `data_quality_status` semantics (OK / WARN / FAIL; status-vs-payment contradictions informational). ADR-004: customer_name and email are pruned at raw landing. ADR-005: sha256-idempotent loads, per-report_date DELETE+INSERT.
- Contracts for customers, orders, payments and the report; layers raw / staging / intermediate / marts / quarantine / audit.
- Honest note: the 12 requirement questions (SLA, retention, who signs off status semantics, masking basis...) were never answered by a human. The approval is a test approval only.

## 8. Evaluator decisions and veto evidence

First evaluator verdict: **VETO** (tag `e2e-build-v1`). The data was correct (264/264 report rows equal to its own recomputation; every defect matched ground truth), but:
1. `test_r15_gross_revenue_equals_independent_staging_query` errored with a BinderException. The test read `report_date` and `country` from `staging.stg_orders`; the architecture puts them in intermediate. Ruling: **the test was wrong, the build conformed**. It also noted the test protected nothing (it failed identically for right or wrong revenue).
2. A builder-authored unit test was flaky (three separate unordered DISTINCT queries), failing once and passing 6 of 6 reruns.
The builder was explicitly not allowed to add columns to staging to satisfy the test; the QE rewrote the oracle (now computed from the raw CSVs with a FULL JOIN, plus a self-check that it can fail), the builder fixed its own flaky test and made raw landing transactional.

Second evaluator verdict: **PASS** for `e2e-build-v2`, after diff review (no loosened assertion or threshold), two green full runs, independent reconciliation (264 = 264 on all 8 columns), ground-truth comparison, idempotency hashes, and mutation tests on a scratch copy:

| Mutation | Caught by |
|---|---|
| duplicates not collapsed | 29 failed / 67 errors (contract stop + tests) |
| pending payments counted as successful | 2 arch tests (the unit suite did NOT catch it) |
| stop rule 0.15 -> 0.99 | 6 tests |
| gross_revenue counts refunded orders | R15 oracle alone fails, plus 2 unit tests |
| revenue from payment_amount | 9 tests |
| orphan payments not quarantined | 27 failed / 67 errors |
| amount_mismatch dropped from WARN trigger | 28 failed / 67 errors |

The PASS is limited to this one synthetic snapshot. Veto power was exercised for real; it was triggered by a defect in a test, not by a defect in the data or pipeline.

## 9. Deployment gate results

All local; "release" = a directory with `db.duckdb` and `manifest.json`, "live" = a `current.json` pointer that nothing consumes. No real environment exists.

- `release stage` on the clean data -> release `20261121-214742-956`, smoke passed (5 checks: exit code, not STOPPED, mart non-empty 264 rows, R10 schema, no PII), manifest with raw sha256 values. `status` -> `current: null`: staged, not live.
- `promote` with no approver, `""` and `"   "` -> `ApprovalRequired`, exit 1 each; `rollback` with none or `""` -> exit 1. `current.json` never created.
- Smoke negative: staging the `f1_invalid_dates` input (20.6% excluded) and the `f3_payments_empty` input -> `SmokeFailed`, exit 1, `smoke_failed.json` written, no manifest.
- **No promotion with any approver was run**, no approver name was invented; `TEST-APPROVAL.md` records the approver as UNSET.
- Not exercised: the promote/rollback success paths and the "never staged" refusal (covered by builder unit tests only; the deployment run could not reach that refusal without supplying an approver).
- What a real gate lacks: the approver check is a non-empty-string test (any string passes; no identity, signature, timestamp or ticket link); the pointer file is hand-editable; failed-smoke directories stay in `releases/` and `status` lists them as releases; no tamper check between smoke and promote; no config diff against live; no post-promotion health check or lock.

## 11. Missing capabilities and blockers

1. Agents are not natively runnable here; orchestrator cannot delegate; tool limits are untested (section 0).
2. `src.conformance` needs a dbt project; the scenario has none (ADR-002), so repo conformance is BLOCKED. Rules R1-R23 were instead verified by 204 scenario tests, which is a different, unvalidated checker.
3. Conflicts and gaps in the agent definitions (orchestrator, plus my own reading): quality-engineer is told to put checker logic in `src/conformance.py`, contradicting the frozen-baseline rule; evaluator step 6 needs dbt; evaluator, deployment and incident have no Write tool yet their output must be persisted; the requirements-analyst has no shell yet profiling needs one; `src/deploy.py` and `src/incident_cli.py` are bound to the toy schema.
4. Builder wrote code before tests (against the agent definition's tests-first rule).
5. Open ADR items: freshness check stops a rerun more than 24 h after loading unchanged files; reverting to an older already-loaded file is refused and the rollback path is undefined; post-load checks run after raw is committed, so a STOP leaves the new batch in raw while the marts keep the old output.
6. Unexecuted held-out scenarios proposed by the evaluator: late/delta arrival (Q12), a customer changing country, two payments per order, unknown status values, whitespace/case in country, zero/non-numeric quantities, conflicting duplicate copies, concurrent runs and crash mid-run, the 15% boundary, payment_date vs order_date attribution.
7. Unit suite does not catch "pending counted as successful"; only the architecture oracle does.
8. All 12 business questions (SLA, retention, masking basis, who signs off statuses...) are unanswered.
9. Some subagents reported the working directory as "not a git repository" while git worked from the harness shell; their git-based checks were repeated from the harness and the frozen-path diff is empty.

## 12. Prioritised remediation plan

1. Register the agents natively (or ship a runner) and add a test that each agent is invoked with its declared tools; make nested delegation work so the orchestrator is actually autonomous.
2. Replace the approver string check with a real gate (identity, timestamp, audit log, signed pointer, link to an approval record); make `status` show smoke state; clean or mark failed releases.
3. Add a dbt (or equivalent) conformance path so `src.conformance` can run on this project, or extend it to SQL+Python projects.
4. Write ADRs for the freshness-on-rerun and older-file-revert behaviours; document the post-load STOP behaviour.
5. Execute the held-out scenarios, starting with delta arrival (Q12), country changes and conflicting duplicates.
6. Add remediation actions with guardrail tests, then an incident -> evaluator revalidation loop; add previous-batch volume history, real alerting and a scheduler.
7. Add the "pending counted as successful" case to the builder's unit tests; enforce tests-first.
8. Run the same workflow on a second, differently shaped scenario and on a real warehouse before drawing conclusions.

## Readiness assessment (evidence-based)

- **Educational use: yes.** The workflow, ADRs, quarantine design, evaluator veto and reconciliation approach are clear, reproducible and demonstrate a good practice.
- **Open-source experimentation: yes, with the section 0 caveat.** The core ideas work; the agent runtime layer is not demonstrated natively.
- **Real-world data engineering: not yet.** It produced a correct result on one synthetic snapshot with a rule-based checker; it has no delta/late-data handling, no scheduling, no real warehouse, and the remediation and conformance paths are blocked.
- **Enterprise production deployment: no.** Approval gating is procedural, there is no identity or audit trail, no alerting, no concurrency or recovery testing, no security or compliance review, and the 12 business questions are unanswered. Nothing here supports production readiness.
